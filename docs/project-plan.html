01 / 무엇을 만들고, 무엇을 배우는가

제품 목표: CPU·GPU·RAM 사용량과 읽을 수 있는 온도를 약 1초 간격으로 표시하고, 사용자가 정한 임계값에 따라 정상·주의·위험 상태를 보여주는 Windows 데스크톱 앱을 만듭니다.

학습 목표: “이 코드를 어느 파일에 쓰는가”에서 출발해, 화면과 데이터 수집을 왜 분리하는지 설명하고 새 장치 카드를 스스로 추가할 수 있는 수준에 도달합니다.

범위완성 기준
첫 번째 작은 완성가상 CPU 사용량이 화면에 표시되고 값 변경 시 바인딩으로 갱신됩니다.
CPU MVP실제 CPU 전체 사용량과 지원되는 대표 온도, 갱신 상태, 임계값별 색상, 설정 저장·복원이 동작합니다. 온도 미지원 PC에서는 사유를 표시합니다.
최종 기본 버전RAM 물리 메모리 사용량 및 GPU별 사용량·온도를 확장합니다. RAM 온도는 센서가 있는 경우에만 제공합니다. 장치 하나의 실패가 전체 화면을 멈추지 않습니다.
후속 과제시계열 그래프, CSV 기록, 트레이, 시작 프로그램, 알림, 설치 패키지는 기본 버전 이후에 다룹니다.
선생님은 설계·코드 설명·수정 위치 안내·리뷰를 담당하고, 학습자는 앱 코드를 직접 작성합니다. 이 문서는 개발 계획이며 앱 구현 코드는 변경하지 않습니다.

03 / 시스템 구조와 MVVM

MVVM은 역할을 나누는 약속입니다. View는 화면, Model은 데이터, ViewModel은 화면에 보여줄 데이터와 동작을 담당합니다. 실제 PC를 읽는 코드는 Service로 분리합니다. MVVM은 폴더 세 개를 만드는 일보다 책임을 분리하는 데 의미가 있습니다.

② Service → Model센서 읽기

③ ViewModel값·상태 갱신
변경 알림
④ ViewBinding으로 표시

역할프로젝트에서 하는 일넣지 않을 책임

ViewModel표시할 값, Command, 수집 흐름 조정, 변경 알림라이브러리 센서 이름 탐색, 파일 입출력 상세
Model측정값, 단위, 시각, 상태, 설정Brush, Window 등 WPF 화면 타입
Service하드웨어 접근, 상태 판정, 설정 저장화면 컨트롤 직접 변경

인터페이스가 필요한 이유

IMonitoringService는 “측정 결과를 제공한다”는 계약입니다. 가상 값을 만드는 FakeMonitoringService와 실제 PC를 읽는 HardwareMonitoringService가 같은 계약을 구현하면, 화면 코드를 바꾸지 않고 수집 방법을 교체할 수 있습니다. 초반에는 생성자에 서비스 객체를 직접 전달하는 방식으로 의존성 주입을 배웁니다. DI 컨테이너·Prism·여러 계층 프로젝트는 나중으로 미룹니다.

WPF 시작과 종료 흐름

처음에는 기존 StartupUri를 유지하고 MainWindow 생성자에서 DataContext를 한 번 연결합니다. 실제 수집 단계에서는 App.xaml.cs를 객체 조립의 시작점으로 옮깁니다. 이때 StartupUri를 제거하고 App에서 서비스 → ViewModel → MainWindow를 만들어 창을 한 번만 엽니다. 창 종료 시 수집 취소 → 진행 중 읽기 종료 대기 → 센서 닫기·해제 순서를 지킵니다.

뷰 이벤트를 연결하거나 창 생명주기를 전달하는 소량의 코드 비하인드는 허용합니다. 계산과 센서 접근은 ViewModel·Service에 둡니다.

05 / 단계별 수업 로드맵

각 단계는 여러 짧은 수업으로 나눕니다. 완료 기준을 직접 확인하고, 코드가 동작하는 이유를 설명한 뒤 다음으로 넘어갑니다.

Step 0 · 실행 환경과 프로젝트 읽기

배울 것 솔루션과 프로젝트, SDK와 대상 프레임워크, 빌드·실행, XAML과 코드 비하인드의 관계.

작성 위치 먼저 기존 App.xaml, MainWindow.xaml, .csproj를 읽습니다. 환경 확인 후 필요할 때만 대상 프레임워크를 수정합니다.

완료 기준 빈 창 실행 성공. App에서 MainWindow가 열리는 경로와 빌드 오류를 찾는 방법을 설명할 수 있습니다.

Step 1 · 정적인 CPU 카드

배울 것 Grid 행·열, Margin/Padding, TextBlock, ProgressBar, 기본 C# 타입과 속성 개념.

작성 위치 MainWindow.xaml. CPU 제목, 고정된 25.0%, 사용량 막대만 만듭니다.

완료 기준 창 크기를 바꿔도 CPU 카드가 읽기 좋게 보이고, 각 XAML 속성의 역할을 설명합니다.

Step 2 · MVVM과 바인딩 첫 연결

배울 것 클래스·객체·필드·속성, 생성자, DataContext, Binding, 이벤트, INotifyPropertyChanged.

작성 위치 ViewModelBase.cs, MainViewModel.cs 생성. MainWindow.xaml의 고정 숫자를 Binding으로 바꾸고 생성자에서 DataContext를 연결합니다.

완료 기준 ViewModel의 CpuUsage 값을 바꾸면 숫자와 막대가 함께 갱신됩니다. 변경 알림을 잠시 빼서 왜 화면이 갱신되지 않는지도 확인합니다.

Step 3 · 가상 데이터와 주기 갱신

배울 것 interface, 구현, 생성자 주입, nullable, Task, async/await, CancellationToken, UI 스레드.

작성 위치 Models와 IMonitoringService, FakeMonitoringService 생성. MainViewModel에 시작·중지 흐름을 추가하고 RelayCommand를 작성합니다.

완료 기준 약 1초마다 가상 값이 바뀌며 중지하면 멈춥니다. 시작을 여러 번 눌러도 루프는 하나입니다. 닫을 때 수집이 종료됩니다.

Step 4 · 임계값 판정과 색상

배울 것 enum, 조건문, 순수 함수, WPF Style·DataTrigger, 표시와 계산 분리.

작성 위치 ThresholdRule, ThresholdEvaluator를 만들고 MainWindow 리소스에 상태별 스타일을 추가합니다. 처음에는 고정 임계값을 사용합니다.

완료 기준 69.9 → 70 → 89.9 → 90%에서 정상·주의·주의·위험으로 바뀝니다. 숫자가 없으면 회색 “확인 불가”이며 0%로 바꾸지 않습니다.

Step 5 · 실제 CPU 센서로 교체 — 첫 MVP

배울 것 NuGet, 외부 라이브러리 캡슐화, 센서 트리, IDisposable, 예외·권한 처리.

작성 위치 HardwareMonitoringService 생성. App.xaml.cs에서 실제 서비스를 조립하도록 변경합니다. 설치할 LibreHardwareMonitorLib 버전은 이 수업에서 호환성을 확인하고 고정합니다.

완료 기준 CPU 전체 사용량과 대표 온도가 갱신됩니다. 센서 ID·종류·이름을 진단으로 확인하고, 권한 부족·미지원은 구분해 표시합니다. 온도 부재로 사용량까지 사라지지 않습니다.

Step 6 · 설정과 저장

배울 것 TwoWay 바인딩, 입력 검증, ICommand, JSON 직렬화, 파일 입출력.

작성 위치 MonitorSettings, SettingsViewModel, SettingsWindow, ISettingsService와 JsonSettingsService를 만듭니다.

완료 기준 임계값·갱신 간격 저장 후 재실행해 복원됩니다. 잘못된 값은 저장되지 않으며 취소는 기존 설정을 유지합니다. 저장 실패·깨진 JSON을 화면에서 안내합니다.

Step 7 · RAM 추가와 카드 공통화

배울 것 리팩터링, ObservableCollection, ItemsControl, DataTemplate, 재사용 리소스.

작성 위치 DeviceCardViewModel 생성, CPU 전용 바인딩을 카드 목록으로 전환. 실제 서비스에 RAM 매핑 추가. 공통 스타일을 Resources로 이동합니다.

완료 기준 CPU와 RAM이 같은 템플릿으로 표시됩니다. RAM 사용률과 사용량/전체 GiB가 일관되며 미지원 온도는 숨기거나 명확히 표시합니다.

Step 8 · GPU 확장

배울 것 여러 장치 식별, 센서 매핑 정책, 장치별 설정 키.

작성 위치 HardwareMonitoringService의 GPU 탐색과 설정 매핑 확장. CPU 화면 코드는 재작성하지 않습니다.

완료 기준 내장·외장 GPU를 각각 식별하고 카드로 표시합니다. GPU가 없거나 센서가 일부 누락돼도 나머지 카드는 계속 동작합니다.

Step 9 · 안정성과 최종 점검

배울 것 문제 재현, 핵심 로직 테스트, 로그, 자원 수명 관리.

작성 위치 실제로 필요한 로직에 한해 테스트 프로젝트를 추가합니다. 임계값 경계·설정 검증·센서 누락 매핑을 검증합니다.

완료 기준 30분 연속 실행, 시작/중지 반복, 설정 복원, 센서 실패, 종료 중 읽기를 확인합니다. 대시보드 자체의 CPU·메모리 사용량도 관찰합니다.

06 / 측정·스레드·상태 규칙

실제 센서 공급자

초기 후보는 LibreHardwareMonitorLib입니다. CPU·GPU·메모리 등의 센서를 지원하는 오픈소스 라이브러리이며, 일부 센서에는 관리자 권한이 필요합니다. 지원 목록이 모든 PC에서 모든 수치를 보장하지는 않습니다. 실제 연동 시 PC에서 노출되는 센서를 먼저 조사합니다. 라이브러리의 공식 설명과 배포 시 라이선스·고지 파일도 함께 확인합니다. 공식 저장소

처음부터 관리자 실행을 강제하지 않습니다. 일반 권한에서 읽을 수 있는 항목을 표시하고, 실패 원인을 기록합니다. 필요한 센서만 권한 때문에 누락되는지 실제 PC에서 확인한 후 실행 정책을 결정합니다.

지표선택·표시 정책
CPU 사용량전체 CPU 부하 센서를 선택합니다. 코어별 값 하나를 전체로 쓰지 않습니다. 도구별 샘플링·계산 방식 차이로 작업 관리자와 정확히 일치하지 않을 수 있습니다.
CPU 온도패키지/다이 대표 센서를 우선합니다. 없으면 확인된 코어 온도 중 최대값을 대체값으로 표시하고 출처를 밝힙니다. 첫 번째 온도 센서를 무조건 선택하지 않습니다.
RAM시스템 물리 메모리 사용량과 전체량을 기준으로 비율을 계산합니다. 가상 메모리·GPU 메모리와 구분합니다. 표시 단위 GiB = bytes / 1024³. 모듈 온도 센서가 노출되지 않으면 미지원입니다.
GPU장치별 대표 코어 부하와 코어 온도를 선택합니다. 엔진별 사용률을 무작정 합하지 않고, 핫스폿·메모리 온도는 별도 지표로 남깁니다. ID를 저장해 이름이 같은 GPU도 구분합니다.

주기 수집과 UI 갱신

  1. 기본 간격은 1,000ms, 설정 가능한 범위는 학습용 정책으로 500~5,000ms로 둡니다. 하드 실시간 보장 대신 주기적인 화면 갱신을 목표로 합니다.
  2. 초반 가상 값은 가벼운 UI 타이머로 설명할 수 있습니다. 실제 수집 단계에서는 취소 가능한 비동기 루프 하나와 PeriodicTimer를 사용하고, 이전 읽기가 끝나기 전에 새 읽기를 겹치지 않습니다.
  3. 동기 센서 호출은 백그라운드에서 실행하고 서비스 접근은 직렬화합니다. async라는 이름만 붙여 UI 정지가 해결됐다고 판단하지 않습니다.
  4. 읽기가 끝나면 Dispatcher를 통해 카드 속성과 컬렉션을 UI 스레드에서 갱신합니다. 수집 시간도 관찰하고 느린 경우 화면을 막지 않습니다. WPF 스레딩 모델
  5. 창 종료 시 CancellationToken으로 다음 수집을 막습니다. 취소 토큰이 이미 실행 중인 동기 센서 호출을 강제 중단하지는 않으므로, 그 호출 종료 후 Computer.Close/Dispose를 수행합니다.

데이터 상태와 경보 단계는 다릅니다

DataStatus는 Pending(수집 전), Available(유효), Unsupported(미지원), Error(실패), Stale(오래된 값)을 나타냅니다. AlertLevel은 Unknown, Normal, Warning, Critical입니다. 유효한 수치에만 임계값을 적용합니다.

처음에는 “수집 중…”을 표시합니다. 읽기 실패 시 마지막 성공 값과 시각을 남기되 “이전 값”임을 표시하고 현재 경보는 확인 불가로 전환합니다. 수집 중 마지막 성공 이후 현재 갱신 간격의 3배가 지나면 Stale로 판정합니다. 의도적으로 중지했다면 “중지됨”을 표시합니다. 오류 시 무한 팝업 대신 카드와 하단 상태를 갱신합니다.

임계값 정책

지표정상주의위험
사용량 예시70% 미만70% 이상, 90% 미만90% 이상
온도 예시75°C 미만75°C 이상, 85°C 미만85°C 이상

위 수치는 UI 학습을 위한 초기값입니다. 하드웨어의 안전 한계가 아니며 장치 사양에 맞춰 조정합니다. CPU·GPU·RAM의 사용량과 온도 규칙을 각각 저장합니다. 미지원 지표의 설정은 비활성화합니다.

검증 조건은 Warning < Critical입니다. 사용량은 0~100% 범위, 온도는 섭씨의 유한 숫자로 입력받고 NaN·무한대·빈 값은 거부합니다. 설정 변경 시 현재 유효값의 상태를 즉시 다시 판정합니다. 경계에서 색상이 자주 바뀌는 문제를 관찰하면 후속 단계에서 히스테리시스를 추가합니다.

설정 복구

파일이 없으면 기본값을 사용합니다. JSON이 깨졌거나 저장된 값이 유효하지 않으면 원본을 보존하고 기본값으로 시작하며 사유를 표시합니다. 저장은 같은 폴더의 임시 파일에 쓴 뒤 교체하는 방식을 사용합니다. 저장 실패 시 성공했다고 표시하지 않습니다.

07 / 앞으로 수업을 진행하는 방법

  1. 이번 수업의 한 가지 목표: 눈으로 확인할 결과와 필요한 개념을 먼저 설명합니다.
  2. 파일과 위치 지정: 프로젝트에서 어느 폴더에 어떤 클래스를 만들고, 기존 코드의 어디에 넣는지 안내합니다. 네임스페이스·using·교체 범위도 함께 적습니다.
  3. 작은 코드 단위 제공: 학습자가 직접 입력할 수 있는 양으로 나누고 문법과 실행 순서를 설명합니다.
  4. 빌드와 관찰: 예상 화면·숫자·오류 메시지를 제시하고 직접 실행해 확인합니다.
  5. 이해 확인: 값을 바꾸거나 알림을 제거하는 작은 실습으로 원리를 확인합니다.
  6. 리뷰 후 다음 단계: 작성한 코드나 오류 내용을 바탕으로 수정할 부분을 안내합니다. 요청 없이 앱 코드를 대신 수정하지 않습니다.

첫 수업의 구체적인 범위

Step 0에서 현재 빈 창 실행을 확인한 뒤, Step 1에서 SystemMonitor/MainWindow.xaml의 Grid 안에 CPU 제목·25.0% 텍스트·ProgressBar를 작성합니다. 이때 Binding과 실제 센서 라이브러리는 아직 도입하지 않습니다. 먼저 XAML 레이아웃을 이해한 후 고정 숫자를 ViewModel 속성으로 바꾸는 차이를 경험합니다.

완성 후 스스로 답할 질문

  • CPU 값이 바뀌었을 때 화면은 어떤 경로로 갱신되는가?
  • 가상 서비스를 실제 서비스로 바꿀 때 View를 수정하지 않아도 되는 이유는 무엇인가?
  • 온도 0°C와 온도 센서 미지원은 데이터에서 어떻게 구분하는가?
  • GPU를 하나 더 표시할 때 기존 CPU 코드를 복사하지 않고 확장할 수 있는가?
  • 수집 중 창을 닫으면 센서 객체와 비동기 루프는 어떻게 종료되는가?
